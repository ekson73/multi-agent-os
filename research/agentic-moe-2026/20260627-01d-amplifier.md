## 4. Padrões MoE / Gating Network — Extração e Reuso

### 4.1 Como Ruflo Roteia Agentes (Queen Topology)

O gating network do ruflo opera em dois níveis:

**Nível 1 — Topology Selection (macro-routing):**
```
Router recebe tarefa
  → Avalia: paralelismo necessário? coordenação de consenso? latência?
  → Seleciona: Hierarchical (Queen-Raft) | Mesh (Gossip) | Adaptive (Byzantine)
```

**Nível 2 — Agent Dispatch (micro-routing):**
```
Queen recebe tarefa + contexto HNSW
  → SONA Micro-LoRA classifica domínio da tarefa
  → MoE Attention routes para top-K agentes especializados
  → AgentDB recupera padrões similares do passado (ReasoningBank)
  → Workers executam em paralelo ou sequência
  → Resultado consolidado via consensus protocol
```

**Estado mantido:**
- AgentDB: vetores de tarefas + outcomes (HNSW, SQLite)
- ReasoningBank: `{sessionId, task, input, output, reward[0-1], success, critique, tokensUsed, latencyMs}`
- Trust scores de federation: histórico de comportamento por agente remoto

**Padrão reutilizável para o Hub:** O ciclo RETRIEVE→JUDGE→DISTILL→CONSOLIDATE (4 fases do learning loop) é um primitivo de memória episódica que qualquer HUB pode adotar sem reimplementar. O gating `89% accuracy via intelligent routing` aponta para classificação semântica de tarefa + lookup HNSW como mecanismo central.

### 4.2 Como BMAD Roteia Agentes (Persona Handoff)

O gating network do BMAD é **stateless e declarativo**:

```
Usuário descreve situação/necessidade
  → bmad-help analisa: "Em qual fase do SDLC você está?"
  → Mapeia fase → persona responsável
  → Handoff contextual (persona assume a sessão)
  → [opcional] Party Mode: múltiplas personas ativas para debate
```

**Gating signal:** A fase do projeto (brainstorm / requirements / architecture / implementation / testing / deployment) é o sinal de gating. Não há vetor de embedding — é roteamento simbólico/declarativo.

**Estado mantido:**
- Artefatos gerados (PRD, ADR, specs) persistem no filesystem do projeto
- Sem memória episódica entre sessões (cada sessão de IDE começa fresh)

**Padrão reutilizável para o Hub:** O mapeamento `fase_do_projeto → persona_ativa` é um esquema de gating hierárquico de baixo custo computacional, extremamente interpretável. Para contextos onde o overhead de HNSW é desnecessário (projetos simples, budgets pequenos), este padrão é preferível.

### 4.3 NanoClaw (ECC — Grupo 1c) como Terceiro Exemplar

O NanoClaw (de grupo 1c) representa o extremo oposto: gating **ultra-leve** via regras de pattern matching sobre o tipo de token de código. Não há LLM intermediário no roteamento — o compilador/linter decide qual "expert" (transform) aplicar. Reutilizável em contextos onde a decisão de routing pode ser determinística (e.g., roteamento por tipo de arquivo, linguagem ou tag de domínio).

### 4.4 Tabela Comparativa de Gating Patterns

| Dimensão | Ruflo (Queen/HNSW) | BMAD (Persona Handoff) | NanoClaw (Rule-based) |
|---|---|---|---|
| Mecanismo de routing | MoE Attention + HNSW semantic search | Fase do SDLC → persona map | Pattern matching determinístico |
| Custo computacional | Alto (embedding + vector search) | Baixo (simbólico) | Mínimo (O(1) lookup) |
| Adaptabilidade | Auto-learning (reward signals) | Estático (versão do framework) | Estático (regras) |
| Interpretabilidade | Médio (black-box MoE) | Alto (persona explícita) | Muito alto (regra visível) |
| Estado entre sessões | Sim (AgentDB persistente) | Não (filesystem apenas) | N/A |
| Ideal para | Tarefas complexas, ambíguas, alta paralelização | Processo de desenvolvimento estruturado | Transformações determinísticas |

### 4.5 Recomendações DRY para o Hub

O Hub **NÃO deve reimplementar** os seguintes padrões — deve referenciá-los e integrá-los:

1. **Learning Loop 4-fases (RETRIEVE→JUDGE→DISTILL→CONSOLIDATE):** Adotar do ruflo como primitivo de L8 Memory. Implementação via AgentDB/ReasoningBank pode ser consumida via MCP tools.

2. **Persona-to-Phase mapping table:** Extrair do BMAD como esquema de gating declarativo de baixo custo. Útil como fallback quando contexto é insuficiente para routing semântico.

3. **Behavioral Trust Scoring formula:** `0,4×success + 0,2×uptime + 0,2×threat + 0,2×integrity` do ruflo é diretamente reutilizável para o Hub avaliar confiabilidade de sub-agentes externos.

4. **Queen → Topology Selection:** O padrão de selecionar topologia (hierárquica vs. mesh vs. adaptativa) com base no tipo de tarefa é um meta-routing reutilizável — o Hub pode implementá-lo como primeira camada do gating antes de despachar para L3 experts.

### 5.2 Quando Orquestração Pesada é Over-Kill

Ruflo traz overhead significativo que não se justifica em todos os cenários:

**Contextos onde ruflo é over-kill:**
- Projeto solo, budget limitado de tokens: os 27 hooks + daemon + MCP server adicionam latência e custo sem ganho
- Tarefa simples e bem-definida (ex: "refatore esta função"): não precisa de swarm, Queen, ou consensus protocol
- Prova de conceito ou protótipo: o tempo de setup (`npx ruflo init` + configuração de federation) supera o valor entregue
- Ambiente sem persistência (CI efêmero): AgentDB e ReasoningBank perdem valor sem sessões longas
- Equipe sem expertise em TypeScript/Node: 35 plugins com dependências npm são difíceis de auditar

**Contextos onde BMAD é over-kill:**
- Tarefa única sem processo de planning (ex: debug de bug específico)
- Ambiente que já tem orquestração de processo (e.g., Linear + Jira) — BMAD duplicaria artefatos
- Contexto onde memória entre sessões é crítica — BMAD não persiste aprendizado

**Regra prática para o Hub:** Usar BMAD (ou padrão equivalente de persona handoff) quando o gating pode ser simbólico e o projeto tem fases claras de SDLC; reservar ruflo (ou seu learning loop) quando há necessidade de memória adaptativa cross-session, paralelização real de sub-agentes ou security runtime.

### 5.3 L3 sobre os Substratos — Dependências de Camada

L3 (Amplifier) não é autossuficiente. Ambos os experts dependem implícita ou explicitamente de:

| Camada | Dependência em Ruflo | Dependência em BMAD |
|---|---|---|
| L8 — Memory | AgentDB HNSW, ReasoningBank (explícito e profundo) | Filesystem de artefatos (superficial) |
| L9 — Observability | ruflo-observability (structured logs, traces, metrics); cost-tracker | Nenhum nativo; depende do AI IDE |
| L0 — Guardrails | AIDefence, ruflo-security-audit, input validation | Nenhum nativo — delega ao IDE/LLM |

**Implicação para o Hub:** Um HUB que usar ruflo como L3 expert DEVE provisionar L8 (AgentDB ou equivalente) e L9 (observability stack) para que o sistema funcione. BMAD pode ser integrado mais levemente mas entrega menos valor sem L8.
