## L1 — Spec-Driven Development (SDD)

A camada onde a intenção humana vira um artefato executável **antes** do código. Eixo central de tensão do sublayer: **formal/template-rich (Spec Kit)** vs **leve/iterativo (OpenSpec)** vs **anti-context-rot por subagentes (gsd-core)**.

### L1.3 · open-gsd/gsd-core

**Identidade & maturidade.** Tagline: *"Git. Ship. Done."* — *"a light-weight meta-prompting, context engineering, and spec-driven development system"* para Claude Code, OpenCode, Gemini CLI, Kilo, Codex, Copilot, Cursor, Windsurf. Rodapé: *"Claude Code is powerful. GSD Core makes it reliable."* Licença **MIT** (confirmada). Linguagem **Node/JS** (npm `@opengsd/gsd-core`); instalação `npx @opengsd/gsd-core@latest` (escolhe runtime + global/local) → `/gsd-new-project`. **Branch default `next`.** **~4.2K★** [sec] (RUN 0; o sibling `get-shit-done-redux` ~583★; o original tinha 65k+★) · MIT. **É o sucessor SEGURO do GSD** — ver postura de segurança.

**Propósito.** Combate o **context rot** — *"the quality degradation that accumulates as an AI fills its context window"* — rodando pesquisa/planejamento/execução pesados em **subagentes de contexto fresco**, mantendo a sessão principal enxuta. Três modos de falha visados: context bloat, ausência de memória compartilhada entre sessões, e nada verificando que o código funciona.

**Capacidades.** Loop de 5 fases (uma por vez, por milestone): **Discuss** (→ `CONTEXT.md`) → **Plan** (pesquisa/decompõe/verifica caber em contexto fresco) → **Execute** (waves paralelas; cada executor recebe 200k tokens limpos) → **Verify** (percorre o construído, diagnostica + corrige antes de "done") → **Ship** (cria o PR, arquiva a fase). Comando de entrada `/gsd-new-project`; demais nomes em `docs/COMMANDS.md` [UNVERIFIED além do entry]. Artefatos: `STATE.md` ("the spine of the system": milestone/fase/decisões/blockers/progresso) + `CONTEXT.md`; *"structured artifacts survive session boundaries."* Orquestração a mais sofisticada do sublayer (thin orchestrator + subagentes frescos + verify-before-done). Cobertura provider-flexível (público + local), contraste deliberado com o `gsd-plugin` Claude-only.

**Lentes.**
- *OSS posture:* MIT, fork comunitário (open-gsd) com migração bit-for-bit e atribuição preservada.
- *S-SDLC fit:* **Forte na orquestração** — verify-before-ship + PR auto-gerado + worktree-isolated; memória cross-sessão.
- *SaaS multi-tenant fit:* Indireto.
- *SDD-methodology fit:* **SDD + context-engineering** — leve no core, pesado na orquestração por subagentes.
- *MoE expert-profile:* L1 Spec; papel **context-rot orchestrator**; competência alta (orquestração); persona "shipper disciplinado anti-bloat"; abstração média-alta; autorização: filesystem + worktree + PR + subagent dispatch (A2A-like).

**Segurança — A HISTÓRIA DE SUPPLY-CHAIN (headline do sublayer).** O `open-gsd/gsd-core` atual é o **fork SEGURO**; o **original `gsd-build/get-shit-done` por "TÂCHES" está EXCLUÍDO/comprometido**. Confirmado por múltiplas fontes independentes (anúncio fixado do mantenedor do fork + firma de segurança + imprensa cripto):
- **Rug-pull confirmado:** o criador lançou um token Solana `$GSD` na esteira do hype (venceu o Bags Hackathon), drenou liquidez, vendeu tokens e **deletou contas X + GitHub**, sumindo com ~US$500K (~2026-04). Mantenedor: *"the `$GSD` token… has been publicly linked to a rug-pull."*
- **Fork (`get-shit-done-redux` → `open-gsd`)** em 2026-05-22: espelhou 394 branches/229 tags/77 issues/17 PRs, preservou código + MIT + atribuição, removeu badges de token e links sociais mortos. Versionamento resetado para v1.0.0 (quebra limpa do 1.42.x).
- **Ameaça NPM ativa e contínua (a parte mais séria):** *"The scammer still holds the administrative keys to the original NPM package registry."* Como o GSD requer permissões profundas de `shell/bash`, um update malicioso aos pacotes ORIGINAIS poderia comprometer máquinas locais (chaves privadas, env vars). **Pacotes npm originais permanecem vivos.**
- **Remediação:** desinstalar originais (`npm uninstall -g get-shit-done-cc`, `@gsd-build/sdk`), limpar `~/.npm/_npx/`, apagar pastas `gsd` não-Markdown em `.claude`; usar apenas `@opengsd/gsd-core`; pinar versões; sandboxar o agente.
- **O código do fork em si:** auditoria independente — *"No backdoors or active malicious payloads"*; o risco está inteiramente nos pacotes ORIGINAIS. (Identidade legal do fundador reportada na imprensa cripto mas [UNVERIFIED].)

**Superfície de integração.** `{filesystem, git-branch, git-PR, git-worktree, memory, rules, subagent-orchestration (A2A-like)}`. Memória = `STATE.md`/`CONTEXT.md` cross-sessão (file-backed); Ship cria PR com body gerado; worktrees isolados (re-tentativa em worktree estreito ao rejeitar). **Sem** MCP/P2P/ticket/webhooks/TCP [UNVERIFIED]. Mecanismo definidor: orchestrator → subagentes de contexto fresco reportando de volta.

## (3) ANÁLISE CRUZADA DO GRUPO — overlaps, colaboração vs competição vs incompatibilidades (com evidência)

### (a) OpenSpec vs Spec Kit — leve/iterativo vs formal/template-rich
**Competição direta, mesma vaga (a camada de spec do projeto).** O próprio OpenSpec se posiciona contra o Spec Kit: framing de "Thorough but heavyweight… OpenSpec is lighter" e filosofia *"fluid not rigid, iterative not waterfall."* **Evidência de divergência:** Spec Kit é phase-gated (constitution→specify→plan→tasks→implement, com `clarify` obrigatório e `checklist`/`analyze` como gates), escreve `.specify/`+`specs/NNN/`, cria branch+Issues+PR; OpenSpec é **git-agnóstico** (organiza `openspec/changes/<name>/` folders, *"update any artifact anytime"*, sem gates). **Incompatibilidade prática:** rodar ambos no mesmo repo gera **dois sistemas de spec concorrentes** (dois diretórios, duas convenções de comando `/speckit.*` vs `/opsx:*`, dois conjuntos de arquivos de guidance do agente) — escolha mutuamente exclusiva na prática. **Quando cada um:** Spec Kit p/ enterprise/compliance/greenfield com governança; OpenSpec p/ brownfield iterativo leve. gsd-core ocupa um terceiro nicho (anti-context-rot por subagentes), ortogonal aos dois mas ainda escrevendo seu próprio `STATE.md`/`CONTEXT.md` — três SSOTs de spec não convergem.

### (b) Superpowers vs GStack vs ECC — a COLISÃO da camada de instrução ("como o agente deve se comportar?")
**A incompatibilidade mais aguda do grupo.** Os três governam comportamento always-on, mas por **mecanismos diferentes e parcialmente sobrepostos** — instalar mais de um cria conflito real:

| Mecanismo de injeção | superpowers | gstack | ECC |
|---|---|---|---|
| Edita/escreve **CLAUDE.md** | Não (instruções de plugin) | **Sim** (`## gstack` + `## Skill routing`) | **Sim** (CLAUDE.md **+ AGENTS.md**) |
| Arquivos **rules/** always-on | Só skill-preamble | Seções CLAUDE.md | **Sim** (`rules/ecc/`, `alwaysApply`, copilot-instructions) |
| **Hooks** (`hooks.json`, por-turno) | Não | Não (roteado por CLAUDE.md) | **Sim** (Pre/PostToolUse/Stop/SessionStart…) |
| **SessionStart context injection** | Não | Não | **Sim** (≤8000 chars) |
| Diretivas "Never use tool X" | Não | **Sim** (bane `mcp__claude-in-chrome__*`) | Implícito via routing |
| Store de **memória** persistente | Não | **Sim** (GBrain) | **Sim** (SQLite+MCP) |
| Bundla **MCP** | Não | só GBrain | **Sim (~14)** |
| Scanner de **segurança** próprio | Não | **Sim** (ML browser/injection) | **Sim** (AgentShield, 102 rules) |
| Footprint / risco de colisão | **O menor** | **Médio-alto** | **O maior** |

**Riscos de colisão co-instalados (com evidência):** (i) **contenção de escrita em CLAUDE.md** entre gstack e ECC (ambos editam; ECC ainda adiciona AGENTS.md); (ii) **gstack bane `mcp__claude-in-chrome__*`** enquanto ECC e outros bundlam/esperam tooling MCP de browser — **conflito direto de política de ferramenta**; (iii) o **próprio README do ECC alerta "Duplicate hooks file detected" / "duplicate execution"** — pioraria com qualquer outro instalador de hooks; (iv) **erosão de contexto empilha** — ~14 MCP servers do ECC + preâmbulo SessionStart 8000-char + seções CLAUDE.md do gstack + skill-preamble do superpowers competem pela janela (ECC documenta 200k→~70k); (v) três camadas de instrução independentes assertando workflows "mandatory" = **precedência imprevisível** em TDD/worktree/review. **Conclusão:** **escolher um, não empilhar.** superpowers é o mais "convivente" (skill-activation, sem hooks/CLAUDE.md-edit); gstack e ECC são os mais invasivos e os mais mutuamente incompatíveis. *(Nota: a suite Kahler — CARL especialmente — é um quarto injetor always-on, com hook por prompt + MCP; CARL+ECC empilhariam dois hook-engines.)*

### (c) PAUL vs GSD — filosofia (in-session+UNIFY vs subagentes+closure-opcional)
**Antagonismo filosófico explícito e documentado** (PAUL nomeia GSD diretamente). Citação verbatim: *"PAUL takes a different approach from GSD."* — tabela contrastando GSD (*Parallel subagents / Optional closure / Static prompts*) vs PAUL (*In-session context / Mandatory UNIFY / CARL dynamic loading*); *"PAUL prioritizes quality over speed-for-speed's-sake."* **A ironia:** gsd-core **também** evoluiu para resolver o mesmo problema (context rot) — mas pela rota **oposta** que PAUL rejeita (subagentes de contexto fresco). São duas teses concorrentes sobre o mesmo mal: **PAUL = manter contexto na sessão + fechamento obrigatório**; **GSD = expulsar trabalho pesado para subagentes frescos**. Incompatíveis por design (não se compõem); um usuário escolhe a filosofia.

### (d) Open Design vs Open CoDesign — borrow explícito (north star vs derivado amplo)
**Colaboração/lineage, não competição hostil** — mas ocupam a mesma vaga (alternativa OSS local-first ao Claude Design). **Evidência citada:** open-design declara open-codesign *"the UX north star and our closest peer"* e lista o que pega emprestado (streaming-artifact loop, sandboxed-iframe preview React 18+Babel, live agent panel, lista de 5 exports). **Divergência arquitetural:** open-codesign = **Electron self-contained** (bundla `pi-ai`, loop **permissionado**, mais polido em surgical-edit/tweaks, +SBOM); open-design = **web+daemon delegando ao seu CLI**, **mais amplo** (mobile/vídeo/áudio, 12 harnesses, mais design-systems) **mas com default de segurança pior** (bypass total de permissões). **Trade-off claro:** open-codesign = lean+seguro+polido; open-design = amplo+multi-harness+arriscado. Coexistem (origem vs derivado), mas para um mesmo job o usuário escolhe um.

### (e) slidev (standalone) vs frontend-slides (agêntico) vs open-design slide export
**Overlap apenas no output (emitir um deck); posicionamentos não-competem.**

| Eixo | **slidev** (tool standalone) | **frontend-slides** (skill agêntico) | **open-design deck mode** (feature de studio) |
|---|---|---|---|
| Natureza | Framework Vue/Vite, human-authored | **Skill** Claude Code (agent-native) | Um modo de um studio completo |
| Input | Markdown (você escreve) | Conteúdo + "feeling" (agente entrevista) | Prompt → agente gera |
| Output | Slides Vue-rendered | HTML single-file zero-dep | HTML decks (guizang-ppt) |
| Dependências | Toolchain Node/Vue/Vite/UnoCSS | **Zero** (CSS/JS inline) | Via daemon do studio + seu CLI |
| Export | PDF / PNG / **PPTX** | PDF + Vercel URL (sem PPTX out) | HTML / PDF / **PPTX** / ZIP / MD |
| Agent-native? | **Não** (2021, predata agentes) | **Sim** (skill propositado) | Sim (studio) |
| Anti-AI-slop | Themes (não slop-focused) | **Explícito** (12 estilos curados) | Sim (DESIGN.md anti-patterns) |

**Diferenciação:** slidev é o polo **maduro/human-first** (runtime mais rico — presenter mode, live coding, LaTeX, Mermaid — mas exige Vue/Vite e não é agent-native); frontend-slides é o **skill agent-native leve** (single-file HTML zero-dep, UX conversacional "3 previews", restrito a Claude Code); open-design deck mode é **uma fatia de um studio multi-superfície** (HTML+PPTX real, 12 harnesses). **Síntese:** quem já vive num agente Claude Code e quer um deck rápido → frontend-slides; quem quer controle/runtime de apresentação maduro → slidev; quem já usa o studio open-design p/ design geral → o deck mode reusa o mesmo pipeline. Não há canibalização — são três tiers (framework / skill / studio-feature) que **convergem só no formato de saída**.

### Síntese de pipeline (o fio que liga L1→L2→L6→L7)
O grupo 1c é uma **esteira**, não um conjunto de concorrentes: **L1** decide *o que* construir (spec), **L2** decide *como o agente se comporta* construindo, **L6** gera *a face* (UI/design), **L7** gera *a narrativa* (slides). As incompatibilidades reais são **intra-camada** (dois specs, dois injetores de instrução, dois studios, dois geradores de slides competem pela mesma vaga), enquanto a composição **inter-camada** é natural (ex.: spec-kit gera spec → superpowers executa com TDD → open-design produz UI → frontend-slides apresenta). A maior armadilha operacional do grupo é **empilhar L2** (superpowers+gstack+ECC+CARL todos always-on) — colisão de CLAUDE.md/hooks/rules garantida.
