# Spec–backlog–ticket reconciler

Reconcile one repository's authoritative specification corpus to its backlog. The repository's observed conventions determine paths and authority; this skill supplies the reconciliation procedure, not a universal file layout. A ticket is an execution view of a source requirement, never a second specification authority. Read [templates/issue-body.md](templates/issue-body.md) before drafting any ticket.

## Inputs and boundary

Obtain the target repository and its owning project, intended ticket destination(s), authorized write scope, and whether this run is plan-only or apply. Discover these from repository configuration and the request; if authority, destination, or permissions remain ambiguous, provide a plan and ask only for the missing decision. Default to dry-run. A write requires explicit authorization for the named repository, destination, and proposed operations; authorization to inspect does not authorize mutation. Respect existing issue governance and project-specific instructions. Never transfer private source material into a different repository, organization, or tracker without explicit scope authorization. No provider SDK, new MCP service, or provider-specific mutation script is required: use the available native MCP/CLI with its documented pagination and write semantics.

**Write dependency:** The bundled [red-team](../red-team/SKILL.md) decision procedure is required to evaluate every hard trigger before apply. A standalone installation without it is plan-only: HOLD all writes until that dependency and an authorized independent verifier are available. Never infer that omitted triggers are false.

## Procedure

1. **Discover authority.** Inspect repository guidance/configuration and actual spec, backlog, and tracker artifacts. Establish the project boundary, authoritative source per requirement, accepted/current versus proposal/delta status, and existing issue-link convention. Do not assume any conventional directory exists. A candidate adapter activates only on observed files and their semantics:
   - OpenSpec: active change proposals, delta specs and tasks represent pending work; accepted/main specs establish the accepted behavior contract, not proof that implementation is complete. Check authoritative backlog/tasks for explicit pending implementation of that contract. Preserve the change and requirement identity; do not re-ticket accepted behavior solely because it exists.
   - SpecDD: inspect observed `.sdd` locality and its spec/task associations.
   - Spec Kit: constitution is project-wide policy; feature spec/plan/tasks supply actionable work. A `taskstoissues` output is an inventory candidate, not independent authority.
   - BMad: relate observed specs, epics and stories; `tickets.toml` may already map tickets. Avoid creating an issue for both a parent and each child when they describe the same unit.
   - Kiro: relate requirements, design and tasks by feature; split by pending executable outcome, not document count.
   - AI-DLC: inspect actual unit-of-work artifacts and their completion state, without assuming vendor paths.
   - Tessl or generic SDD: include only an observed actionable source with a stable identifier and ownership, not a tool's presence or context bundle alone.
   If multiple systems describe one outcome, select the repo-designated authority and retain the others as references. If none is designated and overlap changes identity or status, block that row pending a choice.
2. **Classify and extract.** Build one row per pending, independently verifiable outcome (or a project-defined story/task granularity), with canonical source ID, repository-relative scoped path, acceptance evidence, dependency, and source status. Scope may be a whole file or change with a stable exact path and ID; require a precise heading/section anchor or range when the row addresses only part of a file. Stable identity is `repository identity + canonical source ID + scoped path (+ section when applicable)`; when sources lack IDs, record the most stable observed heading/anchor and explicitly flag instability before writes. Distinguish pending from completed, superseded, rejected, and already-accepted baseline. A broad BRD/PRD is context; an actionable story or requirement under it may be a row. ADR/DDR/RFC are decisions: ticket only a distinct pending action they mandate, linking the decision. EARS, BDD, TDD, ATDD and DDD are expression/development methods; TLA+/SMT are proof techniques, not automatic issues. MIT, PR, FAQ and IETF are ambiguous labels: resolve meaning from context before classification; abbreviations alone create no rows. Never proliferate issues per document, method, proof, or heading.
   Classify spec acceptance separately from implementation state: an accepted spec linked by authoritative backlog/tasks to explicit pending, verifiable implementation is a pending outcome with the accepted spec as its contract and source link. Acceptance alone neither proves implementation complete nor warrants a ticket. Without such pending evidence, accepted baseline is not a new execution outcome; completed, superseded, and rejected outcomes are not pending.
3. **Inventory all destinations.** Enumerate local backlog records and every configured GitHub/Jira/Linear project destination using native MCP/CLI. Page to exhaustion over both open and closed/resolved/archived states (as supported), retaining project/repo scope, issue key/URL, status, body, source links/IDs and pagination cursor/count evidence. Search may help locate candidates but is not a complete inventory. If an endpoint is inaccessible, pagination incomplete, or permissions insufficient, mark the affected destination incomplete and block all writes (creates and updates) there; report its rows for review, never infer absence or uniqueness from a truncated search. Keep separate destination inventories when multiple trackers coexist. Check native provider semantics rather than assuming uniform issue lists: GitHub Issues REST may include PRs (exclude them); Jira Cloud enhanced search uses nextPageToken/isLast and v3 descriptions use ADF; Linear Relay uses hasNextPage/endCursor, can return GraphQL errors with HTTP 200, and archived coverage must be established. Preserve native body formats (e.g., Linear Markdown) when updating.
4. **Match deterministically.** Match within the authorized project by explicit source identity and scoped path provenance (section only for a subset), then inspect candidate issue links in source/local backlog. Normalize harmless URL/anchor formatting only; fuzzy title similarity is review evidence, never automatic equivalence. A backlog unit may intentionally group multiple source artifacts into one issue: accept that match only when the authoritative backlog explicitly maps every source to the same unit and issue, and the issue cites each distinct scoped repository-relative path (and section when applicable). Whole-file or whole-change scope needs the exact path and ID, not a fabricated heading anchor. Preserve all source identities in the match and body; a repeated ID alone cannot establish grouping. Otherwise, one source→multiple issues, multiple sources→one issue, reused IDs at different paths, cross-project collisions, or conflicting source/status evidence are ambiguous: fail closed for those rows and present candidates for manual resolution. A closed issue matching pending work remains a match requiring review, not permission to create a replacement or reopen automatically.
5. **Plan before writing.** Produce a dry-run table containing source identity/scoped path (section if applicable), source status, existing local and remote issue IDs/status, action (`create`, `update`, `no-op`, `review`, `skip`), destination, exact proposed field/body delta, reason, and gate. Pending unmatched→create only after complete inventory and authority checks; pending uniquely matched with stale non-authoritative execution fields→update only after complete inventory; identical→no-op; completed/superseded/rejected or accepted baseline without evidenced pending implementation unmatched→skip; completed matched→review/no-op, never auto-close. Incomplete destination inventory makes even a seemingly unique stale match review-only, not an update. Plan separately for local backlog and each tracker, with links between views rather than duplicate authority. Re-read changed sources and destination records immediately before an authorized write; changed identity or a new collision invalidates the plan.
   Apply the pending rules equally to an accepted-spec contract with authoritative pending implementation: unmatched after complete inventory → create only after authorization and campaign gates; uniquely matched stale execution view → update after those gates. Skip unmatched accepted baseline only when no pending implementation is evidenced; skip unmatched completed, superseded, or rejected outcomes. Never create another issue for a matched accepted-pending outcome.
6. **Apply guardedly.** Obtain explicit approval of the dry-run operations and scope unless the user already explicitly authorized those exact changes. Before the first write, assess the entire proposed campaign (all local backlog and tracker destinations together), not each row in isolation, using `red-team`: assess autonomy, rate, and aggregate blast of side-effecting writes in a window for H11 (a campaign trigger, not a fixed count); unattended effects trigger H4, cross-org/external disclosure H7, and external or untrusted source content steering a write H10 independently. Two attended, low-risk writes do not automatically trigger H11 or HIGH criticality. Apply the other hard triggers and HIGH criticality (risk, impact, reversibility) as well; explicit approval does not waive a mandatory adversarial gate. On any hard trigger or HIGH criticality, first classify the verifier model/provider as a separate disclosure destination and establish explicit authorization to share a minimized plan with it. Redact private source text, secrets, personal data, and unrelated fields; send only the source identities and scoped references, destination scope, proposed deltas and gate evidence needed to challenge identity/collisions and authorization. Do not send the full private plan by default. Obtain an independent verifier distinct from the author, tasked to break this redacted campaign plan (identity/collision, destinations, disclosure, and proposed deltas), using at least 2–3 orthogonal adversarial lenses. If no independently verifiable, authorized destination can receive even the minimized plan, HOLD the high-risk campaign and request an approved verifier or disclosure scope. Enforce independence with the existing `bin/convergence-guard` when present; REFUSE, missing/ambiguous results, or no independent verifier at HIGH means **HOLD all writes**, not self-approval or a forced pass. Record trigger, verifier/gate outcome, and disposition in the dry-run plan. Do not automatically write after the gate: apply only the approved operations once both authorization and any mandatory independent red-team pass. Before any create, require provider-backed idempotency/uniqueness for the canonical source identity or enforceable exclusive single-writer coordination spanning every worker/host for this destination and campaign. A process-local lock or pre-create search alone is not sufficient. If neither is available, HOLD autonomous creates and request explicit single-writer coordination; continue read-only planning and independently eligible updates. Under authorized single-writer coordination, re-enumerate matching identity immediately before each create and again after it; if a collision appears, stop further creates and report it for review. This check detects but cannot guarantee atomicity without provider enforcement or effective cross-worker exclusivity. Render the single canonical issue body template; minimize quoted source text, point to the source instead. Write only planned create/update operations through native MCP/CLI, preserving user-owned fields and existing discussion. If the provider replaces the entire issue body on edit (e.g., GitHub CLI), change only a clearly delimited managed region or surgically merge the approved delta into the latest body; preserve all unowned notes, checklists, and comments. If ownership or layout is ambiguous, mark review and do not write. Do not rewrite source specifications from tickets, auto-close/reopen/delete issues, or mutate other repositories. If a write fails or its outcome is uncertain, re-inventory the affected destination before any retry; do not blindly create again.
7. **Verify.** Re-read every written issue and affected local backlog entry from the destination; check source identity, link, acceptance/dependencies, state, and fields against the approved plan. Report created/updated/no-op/review/skipped rows, unresolved collisions, incomplete inventories, and any write/read-back discrepancy. A partial run is reported as partial, not success. Re-running unchanged inputs must produce no new issues or edits.

## Canonical issue body

Use [templates/issue-body.md](templates/issue-body.md) as the one reusable execution body for both a local backlog item and a remote issue where its native structure permits. This single template covers the informal names **spec-as-prompt** and **ticket-as-spec**: it gives the executor in/out scope, constraints and gates, a verification method with planned versus observed evidence, source provenance, and a concrete next action. The cited specification remains authoritative for requirements; the ticket is only an operational mirror. Do not create a parallel template or treat ticket prose as a revised spec. Populate all fields with sourced facts; `none known` is allowed for dependencies, but unknown acceptance or outcome blocks create. Source status is observed, not inferred from ticket state. Native status fields and project policy govern workflow; the body records the observed status and next action without becoming a second status authority. If a tracker requires separate fields, map the sections once and retain the source provenance in the body. A distinct reference view (e.g., source-side link index or backlog mapping) contains only source identity ↔ issue URL/key, not copied specification prose.

## Synthetic decision check

| Source | Complete inventory / match | Outcome |
| --- | --- | --- |
| Pending `REQ-7` | Complete, unique open issue with same ID/path/section; body unchanged | no-op |
| Pending `REQ-8` | Complete, no issue in open **or closed** inventory | create after authorization |
| Pending `REQ-9` | Complete, unique issue with stale acceptance; source still authoritative | update proposed execution view after authorization |
| Pending `REQ-10` | Complete, two matching issues or shared ID across paths without authoritative grouping | review; no write |
| Pending `REQ-11` | Closed issue matched | review; no replacement/reopen |
| Completed `REQ-12` | No matching issue | skip; no retroactive issue |
| Completed `REQ-13` | Unique open issue | review; never auto-close |
| Pending `REQ-14` | Search result only, next page unavailable | inventory incomplete; block create and update; report review |
| Pending `REQ-14U` | Visible unique open issue is stale, but destination has an unavailable next page | review; block update until complete inventory |
| Pending `REQ-15A` and `REQ-15B` | Complete, authoritative backlog maps two whole-file changes to one unit and issue citing both exact paths/IDs, no section anchors; body unchanged | one grouped match; no-op, no duplicate |
| Pending `REQ-16A` and `REQ-16B` | Complete, one issue mentions both but backlog has no explicit grouping | review; no write |
| Pending `REQ-17A` and `REQ-17B` | Complete, unattended rapid tracker-create campaign with aggregate blast (H4/H11); no independent verifier | HOLD both writes despite approval; no self-review substitute |
| Pending `REQ-17F` and `REQ-17G` | Complete, two attended low-risk reversible writes, no other hard trigger or HIGH criticality | H11/HIGH not automatic from count two; apply ordinary authorization and write gates |
| Pending `REQ-17C` | HIGH campaign, independent cross-provider verifier would receive private plan but sharing not authorized | HOLD all writes; request authorization for minimal redacted plan or an approved independent verifier |
| Pending `REQ-17D` | HIGH campaign, separately authorized verifier receives only redacted identity/destination/delta/gate evidence and passes independent review | proceed only after remaining write gates pass; never disclose full private plan by default |
| Pending `REQ-17E` | Two concurrent workers see same absent identity; no provider idempotency/unique key or enforceable shared lease | HOLD autonomous create; request exclusive single-writer coordination; local lock/search insufficient |
| Accepted spec REQ-18 with authoritative backlog task explicitly pending verifiable implementation | Complete open/closed inventory; no matching issue for the same source ID/path | create execution ticket with accepted spec link after authorization and campaign gates |
| Accepted spec REQ-19 with implementation completed and no pending backlog/tasks | Complete open/closed inventory; no matching issue | skip; no retroactive issue from accepted baseline |

The check passes only if all eighteen rows follow these outcomes and no duplicate issue is created on an unchanged second pass.
